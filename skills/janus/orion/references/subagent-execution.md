# Executing an approved Orion plan with subagents

Use after Mike approves a plan and picks subagent-driven execution (superpowers:subagent-driven-development). This file covers the Orion- and Hermes-specific parts of that procedure.

## Setup
1. Check the live checkout first. If it sits on the feature branch, idle-check and `git checkout main`: cron builds and runs from that tree. Do all work in a worktree (`git worktree add $TMPDIR/orion-wt-<topic> feat/<topic>`, `ln -s /home/hermes/git/orion/node_modules node_modules`). If `main` has moved since the spec/plan branch was cut (`git merge-base main <branch>` != main's tip), `git rebase main` the docs-only commits first (the branch is local, never pushed) so the implementation fast-forwards onto current main; ledger it as a ruling. Run the baseline suite there (`npx vitest run --maxWorkers=2 && npm run typecheck`, in the background with notify) and record the counts in the ledger. Wait for it to finish before dispatching Task 1: an implementer's test runs alongside it on this 4-core host trip the CLI-subprocess timeouts.
   - When a task's fixture holds figures measured from the live DB (e.g. per-request usage for a regression test), re-measure them yourself read-only before dispatching, and note the match in the pre-flight table. Reviewers can only check the fixture's internal arithmetic, not its source.
2. Keep the ledger, briefs (`scripts/task-brief PLAN N`) and review packages (`scripts/review-package PLAN BASE HEAD`) in the worktree's git-ignored `.superpowers/sdd/<plan>/`.
3. Extract, once, into files in that directory: the plan's Global Constraints + Review Focus, the implementer template's rules section, and the reviewer and re-review templates' rule sections. Each dispatch then points at those paths. Pasting them into every dispatch bloats the controller's context.
4. Run the pre-flight scan (task pairs that share files or interfaces) and write rulings into the ledger before Task 1. The usual one: a later task needs an accessor the plan never names (e.g. `ToolContext.targetDoc`). Name it in a ruling and carry it into every task that uses it.

   - For a plan that removes a CLI command group, check in the pre-flight scan which kept subcommands are registered under it (`grep -rn "register.*(<group>" src/cli`, e.g. `proposals` lived under `model`) and every live caller of the old path: `grep -o '<group> <sub>[a-z ]*' ~/.hermes/profiles/raymond/cron/jobs.json | sort | uniq -c` and the disclosure watcher's argv lists. A plan's "kept CLI" list can assume a top-level command that doesn't exist yet. Rule on the move (re-register at top level, no alias) and carry it to the deleting task, the docs task and the rollout's cron-prompt step.
   - For every symbol a task moves or deletes, `git grep` its importers yourself and compare with the task's file list. Plans written from a code search still miss callers inside code a later task deletes. Name the extra files in the dispatch as allowed one-line repoints, so the reviewer doesn't flag scope creep.
   - A plan step that a later phase replaces (e.g. per-asset cron prompts that a daemon will retire): rule it interim and minimal in the ledger, and say so in the dispatch, or the implementer polishes throwaway work.
   - **No-change proofs for a removal plan:** capture the baselines yourself before Task 1, with the OLD dist built in a detached worktree and a `.backup` snapshot of the live DB copied fresh for each run. Fix the report day `D` (the earliest default day across assets) and save `report yield <a> --day D --json` x all assets. For ingest, save `data fetch <a> --dry-run --json` reduced to sorted written metric keys plus `sourceId:status`; values and times are not compared because live data moves. A failed source drops its metrics from `written`, so exclude failed-source metrics on both sides when comparing, and ledger it.

5. Batch same-shape tasks: several adapters in one file, each with its own tests, go to ONE implementer as one commit per task, with one review over the range. Record it as a ruling. Keep tasks that touch different layers (schema, ingest, report) as separate dispatches.
6. The ledger lives inside the worktree, so `git worktree remove` deletes it. Never remove a worktree while its plan is mid-execution. Remove it only after the final review, once the rulings are copied into the final message.

## Harness mechanics (Hermes `delegate_task`)
- There is no model argument: every child runs on the session model. A finished child cannot be resumed, so a fix round is a fresh implementer given the brief, the report file and the findings file. The report file is the memory.
- Results arrive only after you end the turn. Append `Task N: dispatched (BASE <sha>)` to the ledger, then stop with a one-line status.
- Give implementers an `output_schema` (status, commits, test_summary, concerns, report_path).

## Per-task dispatch contents
Name the live files outside the repo that the task touches in concept (profile scripts such as `~/.hermes/profiles/raymond/scripts/orion-tick.sh`, the disclosure watcher, cron prompts) as never-edit. Their updates are rollout items the controller ledgers, because implementers otherwise "fix" live wiring from the worktree.
The worktree path. "Never touch /home/hermes/git/orion, no push, no merge, no network, no live DB, never stage node_modules." The brief path and the shared rule files. Interfaces from earlier tasks the brief cannot know. Your rulings for this task, marked binding. The current suite counts. "Name any failing test." The exact commit message and the report path.

- Plan steps that need a `.env` copy or live network (e.g. the dry-run fetch diff, scratch ticks): run them yourself after the task's commit, and tell the implementer to skip that step (ledger it as a ruling). Subagents then never hold secrets or hit live APIs.

## Verify, review, rule
- Verify each result yourself before the review: `git log BASE..HEAD`, `git diff --stat`, rerun the task's focused test files. When an implementer reports an uncaptured one-off failure, rerun the full suite and record the result.
- When the type system forces an implementer to pull work forward (adding to `RUN_TYPES` breaks `Record<RunType, ...>` in `DEFAULT_BUDGETS` and the strict `agent.budgets` schema), accept it with a ledger ruling and tell the later task to skip that part.
- Turn each example in the plan's Review Focus into its own named risk, case by case. A focus item that lists two cases ("no complete day, or a flow that stopped") is often implemented for the first only.
- Any report or summary path must alert when its data is stale, not just when it can't be built. A report built for an old day exits 0 and freezes the Slack block silently, which breaks Mike's silence-means-broken rule. Set the threshold from measured normal lag (the default report day per asset vs today), plus one day of slack. Keep the numbers shown, and raise a distinct error code so the alert says stale rather than unavailable.
- Give every reviewer 2–4 named risks drawn from the spec's invariants ("any route by which a machine-transcript citation reaches an in-signal row"). A focused check per named risk finds the cross-module holes that a diff-only read misses.
- Write each reviewer "cannot verify" item that belongs to a later task as `Carry to Task N:` in the ledger, and paste it into that task's dispatch as binding. An item that depends on live third-party data (e.g. "does the real page reference exactly one entry bundle?") is yours to settle with one read-only probe before the fix round. Record the result in the ledger rather than turning it into a fix.
- Write a findings file (`task-N-findings.md`) with each finding and your binding ruling. The fix implementer and the scoped re-reviewer both read it.
- Check every "controller clarification" you put in a dispatch against the spec's invariants list before sending it. A clarification that loosens an invariant (e.g. "catalysts need no target-doc citation" against "every catalyst cites the document") gets built and passes review as compliant, because the reviewer is told it is binding.
- Before the task that freezes a fixture (the end-to-end test whose JSON a later component consumes), batch the accumulated rulings and reviewer wording fixes into one fix commit. Include a spec section "Amendments made during execution" listing each ruling and the section it amends. Then the fixture captures the final behaviour, and the spec stays the authority for later tasks.
- End-to-end fixture tasks: seed flows as confirmed `api` rows stamped at day end with exact per-quarter sums. Seed the asset's required level metrics (price, supply, emission, staked share, run rate) so a proposal's effect is a number rather than `blocked`. Normalize run timestamps and the config hash in the fixture, keep the real `agent run --json` shape for the consumer, and assert the repo's asset YAML hash pin after any approve-on-a-copy step.

## Review checks for agent-layer changes (the holes reviewers found)
- **Two hashes, don't confuse them.** `TOOL_LAYER_VERSION` and `sha256(OPERATING_RULES)` feed only the agent run's `configHash` (`src/agent/run.ts`, stored on `agent_runs`); the valuation's config hash (`src/app/valuation.ts`) is the asset hash. Bumping the tool layer or editing the rules text therefore moves no asset pin and adds no "config" change to the next signal; the disclosure fixture placeholders its configHash. Say so when reporting such a change.
- **A behaviour change that runs on an existing path (e.g. a new last request on budget exhaustion) breaks tests outside its brief's file list** (run/tick tests whose scripts now take the new path). Accept the minimal edits that keep each test's intent with a ledger ruling, and tell the later tasks that own those files not to undo them.
- **Agent-loop message shape:** appending a user message right after a tool_result user message gives two consecutive user turns. The Messages API documents that it merges consecutive same-role turns, so that is acceptable. If a live run ever 400s on it, append the text as a block to the previous user message instead.
- **Guards must hold after `ledger.commit`, not only in the staged ledger.** A flag that lives only in memory (e.g. `StagedObservation.live`) is lost on commit, and `eligibleObservations` re-decides from the DB row. Route the guarded case through something persisted (e.g. an `observation` proposal) rather than changing eligibility, because eligibility is the valuation path. The covering test: commit, then assert eligibility.
- **A read tool that reports "Orion's own measurement"** (e.g. a flow total feeding a dev finding's `orion_reading`) must sum only active CONFIRMED committed rows. Otherwise the analyst's own staged or provisional figure gets added on top of the fetched rows. Refuse, naming the ids, when any day is covered twice; never return a total in that case.
- Use one shared day-coverage helper (`observationDays` in `src/ingest/time.ts`) for every "which UTC days does this row cover" question. A daily row is stamped at day end (D+1 00:00Z), and a copied loop drifts from that convention.
- **Text cleaners for Slack or for files an LLM later reads:** remove control and format characters (Cc/Cf/...) FIRST, then strip `<@`, `<!`, `<#`, URLs and `<!--` markers, then cap. In the other order, a zero-width space inside `<!channel>` survives the regex and is re-joined into a live ping. Test with the sequence split by `\u200b` and `\x07`.
- **A Python driver of the Orion CLI must treat an error as `exit != 0` or `data.get('error')` being a dict.** Run rows always carry `"error": null`, so a check for an `error` key fails on success. Fake-`node` tests never caught this; the one real end-to-end run did (the digest printed `est $?`). Run the paid acceptance through the real script, not by hand.

## Old-vs-new whatif inside a task
- `git worktree add $TMPDIR/orion-wt-base main` fails because `main` is checked out in the live tree; use `git worktree add --detach $TMPDIR/orion-wt-base main`. Give each tree its own read-only `.backup` DB copy and no `.env`, so one tree's writes can't affect the other's result.

## Stop point
Final-review findings arrive after the task that wrote the followups note: append them to the note's open items (plus any rulings made since) in one docs commit before reporting, so the record is complete when the worktree goes.
Stop where the plan says (usually before merge, live build, first live fetch and any paid analyst run Mike has not approved). Report the per-task commits, the real suite counts, the plan's checklist, and every `Ruling:` line from the ledger with what it costs if wrong.
