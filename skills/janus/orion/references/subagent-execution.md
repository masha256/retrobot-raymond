# Executing an approved Orion plan with subagents

Use after Mike approves a plan and picks subagent-driven execution (superpowers:subagent-driven-development). This file covers the Orion- and Hermes-specific parts of that procedure.

## Setup
0. Put multi-day execution worktrees AND the extracted old-side release in `/home/hermes/git/orion/.worktrees/` (`.worktrees/<topic>`, `.worktrees/rel-<tag>` from `tar xzf /home/hermes/orion-releases/<tag>.tgz`, with `node_modules` symlinked from the execution worktree because a release tgz ships none), not under `$TMPDIR`. That path is excluded in `.git/info/exclude` and is invisible to vitest/tsc. The scratch dir is pruned after 24h idle, which silently deletes a worktree's git-ignored ledger, reports, review findings and any prebuilt release; only the commits survive on the branch. Copy the ledger to `~/.hermes/profiles/raymond/workspace/orion/phase1.5-sdd/` (or the phase's equivalent) after each task. If a ledger is lost anyway, rebuild it from your own dispatch record and say in the followups note which rulings were restored that way.
1. Check the live checkout first. If it sits on the feature branch, idle-check and `git checkout main`: cron builds and runs from that tree. Do all work in a worktree (`git worktree add /home/hermes/git/orion/.worktrees/<topic> feat/<topic>`, `ln -s /home/hermes/git/orion/node_modules node_modules`). When the plan adds or removes dependencies (e.g. a DB driver swap), or the branch stacks on an unmerged phase whose deps differ from main's (the live tree's `node_modules` has no `pg`), run `npm ci` in the worktree instead of symlinking: an install through the symlink would rewrite the live tree's `node_modules`, and a symlink into another phase's worktree breaks when that worktree is removed at its merge. If the base has moved since the spec/plan branch was cut (`git merge-base <base> <branch>` != the base's tip), rebase the docs-only commits onto it first so the implementation fast-forwards. The base is main only when no unmerged phase stack holds the code being built on (SKILL.md, "Pick the base branch"); for a stacked phase rebase onto the stack tip, never main.
   - On the Postgres code, export `ORION_TEST_DATABASE_URL=postgresql://orion_dev@/orion_test?host=/var/run/postgresql` before the baseline. Without it the global setup throws and vitest prints "No test files found", which looks like a broken include, not a missing env var. If the branch is on GitHub for review, re-push it with `--force-with-lease=<b>:<old sha>`. Ledger it as a ruling. Run the baseline suite there (`npx vitest run --maxWorkers=2 && npm run typecheck`, in the background with notify) and record the counts in the ledger. Wait for it to finish before dispatching Task 1: an implementer's test runs alongside it on this 4-core host trip the CLI-subprocess timeouts.
   - When a task's fixture holds figures measured from the live DB (e.g. per-request usage for a regression test), re-measure them yourself read-only before dispatching, and note the match in the pre-flight table. Reviewers can only check the fixture's internal arithmetic, not its source.
2. Keep the ledger, briefs (`scripts/task-brief PLAN N`) and review packages (`scripts/review-package PLAN BASE HEAD`) in the worktree's git-ignored `.superpowers/sdd/<plan>/`. `task-brief` picks that directory itself, named after the plan file's basename, so create the ledger there and not under a shorter name. Write every deferred minor with the exact marker `Task <N>: minor (deferred): ` and every ruling as `Ruling R<n>: `: the final review's triage extract is a grep, and a variant spelling ("minor (deferred -> final wave)") silently drops that item from triage.
3. Extract, once, into files in that directory: the plan's Global Constraints + Review Focus, the implementer template's rules section, and the reviewer and re-review templates' rule sections. Each dispatch then points at those paths. Pasting them into every dispatch bloats the controller's context.
4. Run the pre-flight scan (task pairs that share files or interfaces) and write rulings into the ledger before Task 1. The usual one: a later task needs an accessor the plan never names (e.g. `ToolContext.targetDoc`). Name it in a ruling and carry it into every task that uses it.

   - For a plan that removes a CLI command group, check in the pre-flight scan which kept subcommands are registered under it (`grep -rn "register.*(<group>" src/cli`, e.g. `proposals` lived under `model`) and every live caller of the old path: `grep -o '<group> <sub>[a-z ]*' ~/.hermes/profiles/raymond/cron/jobs.json | sort | uniq -c` and the disclosure watcher's argv lists. A plan's "kept CLI" list can assume a top-level command that doesn't exist yet. Rule on the move (re-register at top level, no alias) and carry it to the deleting task, the docs task and the rollout's cron-prompt step.
   - For every symbol a task moves or deletes, `git grep` its importers yourself and compare with the task's file list. Plans written from a code search still miss callers inside code a later task deletes. Name the extra files in the dispatch as allowed one-line repoints, so the reviewer doesn't flag scope creep.
   - For a removal plan, `git grep` the whole repo (README, `docs/` outside `superpowers/`, `skills/`, `personas/`, asset YAML comments, code comments) for every removed command, key and module name, and assign each hit to a task (usually the docs task). Stale docs and comments otherwise end up in no task's file list.
   - When a task deletes a test file that holds hash pins, note what each pin guarded (e.g. a minimal-fixture hash that caught new schema defaults) and carry an equivalent cheap pin into the config task, so no guard is lost silently.
   - A plan step that a later phase replaces (e.g. per-asset cron prompts that a daemon will retire): rule it interim and minimal in the ledger, and say so in the dispatch, or the implementer polishes throwaway work.
   - **A plan that drops a stored column and derives it instead** (e.g. `observations.source` from provenance): before or while the task builds, measure on prod read-only (`sql-ro`) the distinct combinations of (old column, every candidate input column) with row counts, and drill into any combination that maps to two old values (group by locator keys, adapter name, formula). Give the implementer that matrix as the binding table test, and after the commit run the derivation over every row of a prod copy expecting N/N equal. The old value is often not a function of the new columns alone (an adapter that stamped `api` among `onchain` contract reads; one hand correction among derived rows), and a guess here silently changes conflict and manual-row rules.
   - **A guard that refuses a whole class of readings** (e.g. "this provenance would read back with a different origin, write nothing"): check it against the next phases' planned sources before accepting it. A later phase moving a revenue line to a first-party adapter would have its nightly fetch refused. Prefer recording the missing distinction on the row (a locator key written only when it applies) over refusing, and keep any guard branch that is the only runtime check of a registry, with a test that runs every registered adapter against its declared value.
   - **No-change proofs for a removal or refactor plan** (e.g. a storage layer made async): run them yourself after every high-risk task, not only at the end. A missed `await` passes typecheck and most tests but changes output. Build the branch, then on a fresh `.backup` copy compare old-release vs new-release `report yield <a> --day D --json` x13, `data anomalies --all --json`, `proposals list --json` and `inbox --json` with `cmp`. Keep a built old release in a detached worktree for the whole plan. Capture the baselines yourself before Task 1, with the OLD dist built in a detached worktree and a `.backup` snapshot of the live DB copied fresh for each run. Fix the report day `D` (the earliest default day across assets) and save `report yield <a> --day D --json` x all assets. For ingest, save `data fetch <a> --dry-run --json` reduced to sorted written metric keys plus `sourceId:status`; values and times are not compared because live data moves. A failed source drops its metrics from `written`, so exclude failed-source metrics on both sides when comparing, and ledger it.
   - **Proof for a plan that ADDS report output and reclassifies a few assets** (e.g. a new `incomeStatement` beside legacy keys): three checks, all mandatory once the new key appears. (a) Legacy JSON (new side minus the new key) exactly equal to old, all assets. (b) Parity for the unchanged assets as a committed path map `{asset: [[label, <new dotted path>, <old dotted path>]]}` (support an `[id=x]` array selector); the comparer reads BOTH values from the two report files itself. Pre-computed value triples prove nothing, because they never touch the report. (c) Reclassified assets checked against expected values computed from the OLD side's JSON by the approved formulas. The comparer fails when the new key exists but a map is missing, or when any asset is covered by neither or both maps. Apply every controller ruling that moves a line (e.g. a fee left out of a statement) to the expected-value script too, or it encodes the old treatment.
   - **A packaged release as the old side** (a directory with a `RELEASE` file) refuses every command unless both `ORION_HOME` and `ORION_ENV_FILE=<home>/.env` are set, and it reads its config (`assets/`) from the release dir, not the home. Pass both on every old-side and new-side command (harmless for a dev checkout), including `db migrate` and any `--help` probe.
   - Save each side's raw JSON to a file and reduce it with a script file (`python3 reduce.py <dir>`), not an inline `python3 -c` inside bash: escaped quotes in an f-string break it silently and both sides reduce to empty, so `cmp` reports "identical". Print the counts per asset (sources, metric keys, failed sources) and treat any zero count as a broken proof, not a pass. The same goes for reading remote env output: put `ssh orion-<env> report yield ...` plus the JSON reduction in one workspace script (subprocess + json) rather than `ssh ... | python3 -c`, which can trip a command-approval prompt; a timed-out approval blocks the step and must not be retried.

5. Batch same-shape tasks: several adapters in one file, each with its own tests, go to ONE implementer as one commit per task, with one review over the range. Record it as a ruling. Keep tasks that touch different layers (schema, ingest, report) as separate dispatches.
6. The ledger lives inside the worktree, so `git worktree remove` deletes it. Never remove a worktree while its plan is mid-execution. Remove it only after the final review, once the rulings are copied into the final message.

## Multi-plan phases (one spec, several subsystems)
- Split the work into one plan per branch: e.g. provisioning scripts, the DB conversion, then the daemon/deploy work. Each plan must produce a testable branch on its own. Write the one with no code dependencies yourself, commit it and dispatch its implementer right away, especially when Mike is waiting on it (e.g. scripts he must run before a server is ready).
- Write the dependent plans in parallel with plan-writer subagents. Give each the spec sections it owns, the writing-plans skill path, and the interface it may assume from its sibling, written out verbatim (signatures, table split, which migration holds which tables). Tell them to write the file only and not commit: you commit after checking. The later plan's Task 0 maps its assumed names onto the sibling plan's real ones.
- Plan writers that read the current code find spec errors (stale scope counts, tables still in use, impossible steps). `git grep` the load-bearing ones yourself before you relay them to Mike, and say they were re-checked.
- Ask each plan writer for its sequencing constraints. A branch that switches the storage engine can't merge into main before cutover, because the live install builds from main. Tell Mike, since it means a long-lived branch stack.
- When Mike has authorised a deploy milestone (e.g. staging), order the plan's tasks so the release/deploy path lands first, and move features that don't block the first deploy after it. Rule it in the ledger. Their job handlers must end as a quiet `skipped` with a log line: a stub that fails would retry and alert every night.
- Scripts that need root (sudo-only provisioning) are built and tested by the subagent without root: `--dry-run` as the normal user must list every change; refusal paths (wrong OS, an SSH caller outside the allow list, placeholders left) are tested; and the SQL is run against PGDG binaries unpacked from the `.deb`s into `$TMPDIR` (`dpkg-deb -x`, then `PG_BINDIR=...`), with nothing installed. State in the report what only a real root run on the target OS can prove.

## Harness mechanics (Hermes `delegate_task`)
- There is no model argument: every child runs on the session model. A finished child cannot be resumed, so a fix round is a fresh implementer given the brief, the report file and the findings file. The report file is the memory.
- Results arrive only after you end the turn. Append `Task N: dispatched (BASE <sha>)` to the ledger, then stop with a one-line status. A background `terminal` job you must wait on before dispatching (the baseline suite) can be waited on in-turn with `process_manage` `wait` (capped at 180 s per call; repeat), then read its log.
- Give implementers an `output_schema` (status, commits, test_summary, concerns, report_path).
- When a controller measurement lands while an implementer is still working on the affected files (e.g. the real prod-copy diff shows which allowlist paths actually move), send it with `delegate_task action=steer` instead of queueing a second fix round; mark it "binding, same commit" and give exact paths/values.
- A task with two large commits (e.g. retire a config key across 13 YAMLs + retire a report shape) can hit the child's iteration cap mid-way, leaving commit A done and commit B uncommitted. Plan such tasks as two dispatches. If it happens anyway, the continuation dispatch lists exactly what remains (from the truncated summary), says "keep and finish the uncommitted work", and tells it to be economical with steps.
- Pass `workdir` on every controller `terminal` call during a long execution. The terminal keeps its last cwd, and once that directory is pruned (scratch) or removed (a detached proof worktree), every later command fails with exit 126 before running.
- Append ledger lines with a QUOTED heredoc (`cat >> progress.md <<'E'`). An unquoted one runs every backtick span inside it as a command (a verb quoted in a ruling becomes `job: command not found` and the text vanishes from the line); when you need `$(...)` expanded, write the verbs in plain quotes instead of backticks.
- Never pipe a proof script through `| head` to preview it (`script | tee log | head -80`): when head exits, SIGPIPE kills tee and the script mid-run, so the last steps silently never run. Write the log with `> log 2>&1`, then read it with `read_file` or `tail`.
- An implementer that returns NEEDS_CONTEXT may leave uncommitted work in the worktree. Don't discard it: the next dispatch says "the tree holds the previous attempt's uncommitted work; read its report, keep it, finish it". If a review fix for an EARLIER task must land first (e.g. a schema the uncommitted YAMLs depend on), give both to one implementer as two commits: the earlier task's fix staged by explicit paths, then the remaining work. Running a review in parallel with the dependent next task is fine; ledger the ruling that review fixes get their own commit.

## Per-task dispatch contents
Before a task that edits asset YAML, `grep -rl <each old asset hash> tests` yourself and list every pin in the dispatch, including ones inside e2e tests (e.g. `LIT_HASH` in `tests/agent/disclosure.e2e.test.ts`). Those are that asset's own pins and get re-pinned; "the e2e test passes unchanged" means its fixtures and replay are byte-unchanged (`git diff --quiet -- tests/fixtures`), not that its hash constant is frozen. Without this the implementer stops on a contradiction.
Name the live files outside the repo that the task touches in concept (profile scripts such as `~/.hermes/profiles/raymond/scripts/orion-tick.sh`, the disclosure watcher, cron prompts) as never-edit. Their updates are rollout items the controller ledgers, because implementers otherwise "fix" live wiring from the worktree.
The worktree path. "Never touch /home/hermes/git/orion, no push, no merge, no network, no live DB, never stage node_modules." The brief path and the shared rule files. Interfaces from earlier tasks the brief cannot know. Your rulings for this task, marked binding. The current suite counts. "Name any failing test." The exact commit message and the report path.

- Plan steps that need a `.env` copy or live network (e.g. the dry-run fetch diff, scratch ticks): run them yourself after the task's commit, and tell the implementer to skip that step (ledger it as a ruling). Subagents then never hold secrets or hit live APIs.
- A plan that marks a whole task "controller" because it touches live data (e.g. a proof harness that snapshots the live DB): split it. An implementer writes the scripts and their unit tests against synthetic dirs, with env overrides for the source DB and dist paths, and is forbidden to execute them; you run the real dry run after its commit. Ledger it as a ruling.
- A read-only on-chain probe a later task needs as input (e.g. classifying a fee before its YAML line is written) is yours: run it while the current task's implementer works, write the verdict to a file in the SDD dir, and give the next implementer the verdict, never the RPC key. The same goes for web research a task needs (a citation url plus a verbatim quote for a cited schedule): fetch the page yourself, extract the quote programmatically from the saved page so it is verbatim, check its length against the validator's cap, and write it to `citations.md` in the SDD dir for the implementer.

## Verify, review, rule
- Verify each result yourself before the review: `git log BASE..HEAD`, `git diff --stat`, rerun the task's focused test files. Rerun with the same env knobs the subagent's report names (e.g. `SHELLCHECK=<path>`, `PG_BINDIR=<path>`). If your count differs from the reported one, check your setup before calling it a failure, and report the count from the full-env run. When an implementer reports an uncaptured one-off failure, rerun the full suite and record the result.
- When the type system forces an implementer to pull work forward (adding to `RUN_TYPES` breaks `Record<RunType, ...>` in `DEFAULT_BUDGETS` and the strict `agent.budgets` schema), accept it with a ledger ruling and tell the later task to skip that part.
- Turn each example in the plan's Review Focus into its own named risk, case by case. A focus item that lists two cases ("no complete day, or a flow that stopped") is often implemented for the first only.
- Any report or summary path must alert when its data is stale, not just when it can't be built. A report built for an old day exits 0 and freezes the Slack block silently, which breaks Mike's silence-means-broken rule. Set the threshold from measured normal lag (the default report day per asset vs today), plus one day of slack. Keep the numbers shown, and raise a distinct error code so the alert says stale rather than unavailable.
- **Pipeline cadence that works:** dispatch task N's review together with task N+1's implementer in one `delegate_task` call. When N's review needs a fix round, write `task-N-findings.md` at once but dispatch the fix only after N+1's implementer returns (one implementer in the worktree at a time), paired with N+1's review in the next call. Each fix lands as its own commit on top, and its scoped re-review uses `review-package <head the review saw> <fix sha>`. Ledger the pairing as a ruling.
- A reviewer may run in parallel with the next implementer. Tell the reviewer to read only via `git show <sha>:<path>` / `git diff <base> <sha>`, to run anything in its own `git worktree add --detach /home/hermes/git/orion/.worktrees/rev-<n> <sha>` with `npm ci`, removed with `git worktree remove --force` at the end, and never to edit anything except its findings file. The implementer then never sees the review mid-task. A controller proof that needs a build while an implementer edits the main worktree (e.g. a live ingest comparison) also gets its own detached `.worktrees/` checkout at the commit under test: building in a tree that is being edited mixes two states.
- After a range review, rule on every finding in the ledger, then send ONE fix-wave implementer with one commit. It gets each important finding and the cheap minors, each with a test written first, plus any concerns from the latest task reports. The minors you defer go into the phase's followups note, which that commit creates if it doesn't exist. Then continue with the next task from the fix commit.
- Give every reviewer 2–4 named risks drawn from the spec's invariants ("any route by which a machine-transcript citation reaches an in-signal row"). A focused check per named risk finds the cross-module holes that a diff-only read misses.
- For daemon, scheduler and deploy code, these named risks find real bugs:
  - **Silence means broken:** a nightly, an hourly job, a publish or a deploy that ends with no Slack post, no alert and yet a dead-man ping. Typical causes: an unset webhook counted as delivered, an unset publish target skipped quietly, a report built for a stale day.
  - **Double-run or lost work:** a lease reaped from a job that is still running, a clock jump, two daemons, a drain during a switch, a crash-looping daemon blocking switch or rollback.
  - **Deploy gates:** a non-main commit reaching prod, a soak gate passed by a job that ran on the old release, a half-unpacked release made current, rollback across a migration that rewrote data, any forced-command verb that runs caller text in a shell or prints `.env`.
  - **Environment isolation:** staging writing prod's database, repo or Slack channel, or the reverse.
  - **Value equality:** caches or new block bounds changing a stored value.
  - **Operator jobs on the single worker** (a backfill or rebuild queued by `job run-now`): a clock-only guard around the nightly reopens too early, because the nightly report keeps waiting for its refreshes until slot + `NIGHTLY_WAIT_MS` (3 h) and refresh retries land 10/30 min after a failure. Gate on the newest nightly slot's unfinished `refresh`/`nightly_report` jobs, not on the clock. Post a start line and the run time, since nothing bounds how long the job runs.
  - **Forced-command verbs (orion-remote):** Python `re.match`/`re.search` with a `$` anchor accepts a trailing newline, so validate caller values with `re.fullmatch` (or `\Z`); probe a destructive flag's injection forms (`--metrics=--yes`, `-- --yes`, `--ye`, a list item starting with `-`) and require exit 64 before Orion runs. Any runbook step a verb section prescribes must use a verb the deploy key actually has (there is no drain verb, and `rollback`'s own 30-min drain aborts while a long job runs), so check every doc instruction against the verb table.
  - **Scoped fetch outcomes:** a `--metric`-scoped fetch that comes back `partial` means a source serving a requested metric failed, so the job must fail with the ALERT line. `done` + partial is right only when nothing but cross-check sources failed.
  In the final review before a first deploy, also have the reviewer walk the exact deploy path command by command and list every binary, path, permission and env key the target host still lacks. Required environment keys are refused at daemon start in stage/prod, never defaulted.
- For report-output additions (a new statement beside legacy keys), these named risks find real bugs:
  - **Null discipline:** a not_measured or missing input shown as 0; a figure v1 publishes (e.g. a disclosed stream's growth) coming out null in the new block. A parity pair whose two sides are both null proves nothing, so count null-null pairs per asset on real data and treat them as uncovered.
  - **Failure isolation:** an exception in the new computation failing the legacy report, the tick or the published snapshot instead of an alert line.
  - **Mixed versions in one line:** a Slack/summary line pairing an old-definition figure with a new one (v1 revenue next to v2 gross profit), and a previous release's job row that no longer parses.
  - **Consumers:** every in-process and CLI consumer of the old keys (`git grep` the report loader and `report yield`), including other phases' proof tools that byte-compare report JSON across releases.
- For code that deletes history (a purge verb), the named risks are:
  - **Irreversible loss:** the export must be complete (every column; superseded and rejected rows too) and written before the delete, inside one transaction under the asset run lock.
  - **Over-deletion:** filter every statement by asset; a still-configured metric loses only rows of the requested `source_type`. Clear `latest_levels`/`watch_state`/`fetch_cursors` only for a metric that is entirely gone.
  - **Shared cursors:** an API flow's cursor key is `<sourceId>><metric>` (one per metric), but a transfer scan's key is a hash over token, sink and allowlist that serves several metrics, so it is never deleted.
  - **FK:** check `superseded_by` links in both directions across the deleted set.
  - **Defaults:** without `--yes` nothing is deleted, and the dry run hits the same refusals as `--yes`.
  - **Rehearse on the prod copy before asking for the real go:** dry-run every pair the release block lists and check its counts against prod's own (`sql-ro` count by asset/metric/source_type), run `--yes`, check one export file per call landed, then rerun `report yield <a> --day D` for all 13 and `cmp` against the pre-purge new-side output: a purge of retired or third-party rows must leave every report byte-identical. Put the measured counts into the release block, so Mike's go is on numbers.
- **Allowlist proofs** (a release that may move a known set of report fields: flatten old/new `report yield` JSON and allow only listed paths with `rel`/`abs` bounds, e.g. `tools/phase3-proof/flatdiff.py`): the false-pass holes reviewers find are (a) an unbounded glob over a section (`dilution.*`) that also covers fields the change can't move (a burn rate going to 0 or null passes): give those fields exact `abs: 0` entries, since every matching entry's bound must hold; (b) fields DERIVED from the allowed change (net-of-dilution, per-token, per-FDV, yields) that the plan never listed: enumerate them from the report type and bound each at the change's own percentage, with differences-of-two-terms getting an `abs` bound instead of `rel`; (c) path collisions in the flattener (a literal dotted key vs nested keys; list ids `1` vs `"1"`): escape and type-tag them; (d) a bare `*` glob or a duplicate asset key in the allowlist: refuse both at load. Placeholder entries must allow nothing (`todo: true`) until filled from the first real diff run with exact paths.
- **A config change that removes a series can move the default report day** (an asset stops waiting on the removed series when picking its newest complete day). An explicit `--day D` proof won't show it, so also run `report yield <a>` without `--day` on both sides and report the default day per changed asset.
- **A task MEANT to change goldens** (a config sweep that moves a few report fields): accept the rewrite only after the reviewer flattens `git show <base>:<golden>` vs `<head>:<golden>` with a script and lists every changed path per asset, and none is a revenue, cost, holder-flow, yield, dilution, grade or price path the plan didn't name. Hand the reviewer that method explicitly: the review package of such a task is hundreds of KB, so tell it to diff per file (`git diff <base> <head> -- <path>`) and not read the package whole.
- An implementer's report may end with an orphaned background test process whose captured tail shows failures from an earlier, pre-fix run. Rerun the named files yourself on the committed head before treating them as real or as fixed.
- **An adapter on a rung no adapter used before** (e.g. `disclosure`, which needs `citation_url` on the row): the implementer has to touch shared provenance (`originOf`, `methodOfSource`, the writer's citation guard). Name it as a reviewer risk: prove from the old code (`git show <base>:src/provenance/...`) that every existing row's read-back origin and method is unchanged, especially manual `data set --citation` rows and pre-v2 rows that carry no adapter in their locator.
- Run the real-data proof as soon as a task's commit exists, in a detached `.worktrees/proof-<sha>` checkout (node_modules symlinked from the execution worktree, removed after), even while that task's review fixes are in flight. It catches real-data breaks a round earlier, and its v2 table becomes the gate preview.
- **A task that adds reconciliation checks:** after its commit, evaluate every wired check read-only over the full flow window on a fresh proof schema migrated by the new dist: copy `scripts/eval_checks.ts` (orion skill) into the detached proof checkout's root and run `npx tsx eval_checks.ts <proof home> <last day> 91`; it calls `evaluateChecks` per day and never `recordChecks`. Report per check ok/breach/incomplete and the max gap. A breach on real data is a data finding for Mike with both sides (never a looser tolerance; a dust breach gets a proposed absolute floor as his decision). A check that is incomplete on every day (e.g. a level read at a time outside the check's boundary window) is "can't verify until X", said plainly, not a pass.
- **A history backfill dry run with unmapped rows** (e.g. provenance on old observations): group the unmapped rows by asset/metric/reason, pull their ids, dates, status and notes read-only, and propose one rule per group (with ids) as a decision for Mike. Continue the plan if no task before the gate that needs zero unmapped rows depends on them, and ledger that ruling; never invent a mapping.
- When an implementer relaxes a spec rule so the plan's data fits (e.g. allowing a duplicate id "just for pass-on lines"), rule for the spec and change the data (rename the ids) rather than accept the exception: an exception in validation makes every later consumer (check parts, site keys) ambiguous.
- **The stack base moves mid-plan** (another phase commits to `feat/daemon`): if its new commits touch files the plan's tasks also edit, rebase once after the last task and before the gate report, then rerun the full suite and the proof; ledger it. Rebasing between tasks repeats conflict work, and a test the base fixed (e.g. a clock-dependent one) is named as inherited until then. Rehearse it first: `git worktree add --detach .worktrees/rebase-trial <head>`, `git checkout -b tmp/rebase-trial`, `git rebase <base tip>`, full suite + typecheck + lint there; only when that is clean and green rebase the real branch (confirm `git diff tmp/rebase-trial HEAD` is empty), then remove the trial worktree and branch. A conflict in the trial goes to an implementer, not a hand resolution.
- Write each reviewer "cannot verify" item that belongs to a later task as `Carry to Task N:` in the ledger, and paste it into that task's dispatch as binding. An item that depends on live third-party data (e.g. "does the real page reference exactly one entry bundle?") is yours to settle with one read-only probe before the fix round. Record the result in the ledger rather than turning it into a fix.
- **An implementer's "identical on all N assets" is only as wide as its test.** Check that the golden test compares the WHOLE artefact for EVERY asset (not one asset whole and the rest by a few keys): a pack test that whole-compared only LIT missed a new key on six assets. Golden files must be generated from the base commit (verify by regenerating there and `cmp`), and a golden test must FAIL when its file is missing; one that rewrites a missing golden (regeneration only behind an explicit env flag) passes against itself.
- After a rebase that brings in another asset's config change, regenerate the goldens at the rebased base commit and JSON-diff them against the old ones: only the changed asset may move (synthetic-input goldens often don't move at all, which is fine; any other asset moving = stop).
- Write a findings file (`task-N-findings.md`) with each finding and your binding ruling. The fix implementer and the scoped re-reviewer both read it.
- Check every "controller clarification" you put in a dispatch against the spec's invariants list before sending it. A clarification that loosens an invariant (e.g. "catalysts need no target-doc citation" against "every catalyst cites the document") gets built and passes review as compliant, because the reviewer is told it is binding.
- Before the task that freezes a fixture (the end-to-end test whose JSON a later component consumes), batch the accumulated rulings and reviewer wording fixes into one fix commit. Include a spec section "Amendments made during execution" listing each ruling and the section it amends. Then the fixture captures the final behaviour, and the spec stays the authority for later tasks.
- End-to-end fixture tasks: seed flows as confirmed `api` rows stamped at day end with exact per-quarter sums. Seed the asset's required level metrics (price, supply, emission, staked share, run rate) so a proposal's effect is a number rather than `blocked`. Normalize run timestamps and the config hash in the fixture, keep the real `agent run --json` shape for the consumer, and assert the repo's asset YAML hash pin after any approve-on-a-copy step.

## Review checks for agent-layer changes (the holes reviewers found)
- **Two hashes, don't confuse them.** `TOOL_LAYER_VERSION` and `sha256(OPERATING_RULES)` feed only the agent run's `configHash` (`src/agent/run.ts`, stored on `agent_runs`); the valuation's config hash (`src/app/valuation.ts`) is the asset hash. Bumping the tool layer or editing the rules text therefore moves no asset pin and adds no "config" change to the next signal; the disclosure fixture placeholders its configHash. Say so when reporting such a change.
- **A behaviour change that runs on an existing path (e.g. a new last request on budget exhaustion) breaks tests outside its brief's file list** (run/tick tests whose scripts now take the new path). Accept the minimal edits that keep each test's intent with a ledger ruling, and tell the later tasks that own those files not to undo them.
- **Agent-loop message shape:** appending a user message right after a tool_result user message gives two consecutive user turns. The Messages API documents that it merges consecutive same-role turns, so that is acceptable. If a live run ever 400s on it, append the text as a block to the previous user message instead.
- **Guards must hold after `ledger.commit`, not only in the staged ledger.** A flag that lives only in memory (e.g. `StagedObservation.live`) is lost on commit, and `eligibleObservations` re-decides from the DB row. Route the guarded case through something persisted (e.g. an `observation` proposal) rather than changing eligibility, because eligibility is the valuation path. The covering test: commit, then assert eligibility.
- **A read tool that reports "Orion's own measurement"** (e.g. a flow total feeding a dev finding's `orion_reading`) must sum only active CONFIRMED committed rows. Otherwise the analyst's own staged or provisional figure gets added on top of the fetched rows. Refuse, naming the ids, when any day is covered twice; never return a total in that case.
- Use one shared day-coverage helper (`observationDays` in `src/ingest/time.ts`) for every "which UTC days does this row cover" question. A daily row is stamped at day end (D+1 00:00Z), and a copied loop drifts from that convention.
- **Text cleaners for Slack or for files an LLM later reads:** remove control and format characters (Cc/Cf/...) FIRST, then strip `<@`, `<!`, `<#`, URLs and `<!--` markers, then cap. In the other order, a zero-width space inside `<!channel>` survives the regex and is re-joined into a live ping. Test with the sequence split by `\u200b` and `\x07`.
- **A Python driver of the Orion CLI must treat an error as `exit != 0` or `data.get('error')` being a dict.** Run rows always carry `"error": null`, so a check for an `error` key fails on success. Fake-`node` tests never caught this; the one real end-to-end run did (the digest printed `est $?`). Run the paid acceptance through the real script, not by hand.

## Old-vs-new whatif inside a task
- `git worktree add $TMPDIR/orion-wt-base main` fails because `main` is checked out in the live tree; use `git worktree add --detach $TMPDIR/orion-wt-base main`. Give each tree its own read-only `.backup` DB copy and no `.env`, so one tree's writes can't affect the other's result.

## Proofs that need `.env` or network
- Run live dry-run fetch diffs and scratch ticks yourself (controller), not in an implementer: they need a `.env` copy (delete its `ORION_HOME=` line) and the network. Capture the old-dist baselines in Task 0 (`report yield --day D` on a `.backup` snapshot, and a reduced `data fetch --dry-run --json` = written metric keys + sourceId:status), delete every scratch home holding `.env` right after use, and record a source that failed in the baseline so the diff excludes it.
- **A backfill rehearsal that needs RPC/API keys** (e.g. re-scanning token amounts on a proof copy): write it as one script file run in the background with notify, not inline commands.
  - Copy ONLY the named RPC env keys from the live `.env` into the scratch home's `.env` with a small Python step (never print them), and never the whole file: it carries `ORION_HOME`, the Anthropic and Slack keys.
  - Mask keyed URLs in every captured stderr (`/v2/`, `/v3/`, `api-key=`, `dkey=`).
  - Run assets one at a time; before each, `pgrep` for a prod `dist/cli/index.js|run-daily` process and stop if one is running, because prod shares the Alchemy quota and keyless CoinGecko from this host.
  - At the end, cut the scratch `.env` back to the DB lines.
  - Run the full rehearsal once, on the final commit of the gate. Token re-scans take about 11 s/day per asset on Base, and an unreleased migration edited in place by a fix round changes its sha, so the migrator refuses proof schemas built with the old file. A rehearsal on superseded code spends prod's shared quota twice for numbers you must redo.
  - To stop it, kill by PID from `ps -eo pid,args | grep <script>`: `pkill -f '<pattern>'` also matches the shell running the pkill and kills your own command (SIGTERM, exit -15).
- **Proving a DB-writing backfill left values alone:** before and after the real run on the proof schema, take `count(*)` plus `md5(string_agg(id||':'||value||':'||source||':'||coalesce(source_detail,'')||':'||status, ',' order by id))` over `observations` and require them equal. Then scan the new columns for key patterns (`locator::text ~* 'alch|/v2/[A-Za-z0-9_-]{16,}|apikey|api_key'` must count 0), and rerun the cross-release proof, because the report's new read path (e.g. provenance from rows) is only exercised once the backfill has written.
- **Proof for a `-- breaking` migration** (e.g. a column drop): the old release can't read the migrated schema, so order the script: fresh prod copy (migrated by the old release) -> run the derivation check over every row -> capture the old release's `report yield <a> --day D --json` (v2 and `--legacy`) for all assets -> new dist `db migrate` WITHOUT `--breaking` (must exit 1 with `migration_breaking`) -> `db migrate --breaking` (check `max(schema_migrations.id)` and that the column is gone) -> the new dist's reports -> compare every field (rel 1e-12) with a script file. Rerun it from a fresh copy on the fix-round commit before asking for the release go.
- For a change that must not move VALUES (an RPC call cache, finalized-block bounds, a CoinGecko call batch), reduce both sides to `(metric_key, observed_at) -> value`, not just keys. Closed-day flow rows (stamped at day end) must match exactly. Level rows are stamped at fetch time, so they never pair up; count them as "timestamp only". Both releases can read one imported schema, because a dry-run fetch writes nothing and the newer schema is accepted by the older release.
- When a closed-day value differs, run the same asset old, new, old, new a few seconds apart before calling it a regression. If the OLD release alone moves between runs, the source is unstable: a supply-diff daily flow can still move hours after the UTC close. That is a data finding for Mike and the followups note, not a fault in the change.
- A lag or freshness figure read from a snapshot is pre-fetch; the daily tick fetches first, so production lags are a day shorter. Measure thresholds from a post-fetch scratch tick.
- Before a plan removes a CLI parent command, grep for subcommands registered under it (`registerX(model, ...)`): Phase 1's `proposals` lived under `model`.

## Proofs for a release that deletes or replaces history, and its per-env release block
- A per-day report proof that deletes or replaces a LEVEL series' history (e.g. a `data purge` of third_party unlock rows) must compare a past day too (D-91 or D-7), not only D = yesterday: the D report still reads today's new row (levels are read to the end of D+1), so it hides that every older day's figure turns null. Make such a purge its own gated step in the release block, with the consequence stated, and put the pick to Mike.
- In the release block, save each env's pre-deploy reports before `deploy.sh`, and run the flatdiff check against them right after the switch, BEFORE any `job run-now refresh`: a refresh writes new price/supply levels inside D+1 and moves every market-cap field, so a check after it STOPs on correct values. After the refresh, check the new rows directly (`data show <a> <metric>`) and save a `mid/` set; compare later steps (purges, smoke backfills) against `mid/` with `cmp`, re-saving it if a nightly or another write ran in between.
- Allowlist `abs` bounds derived from a date-dependent count (tranches inside a 365-day window) expire as the window moves; size them for the whole release window and name the last valid date in the entry's reason, or use `rel` bounds.
