# Orion on kanban (live since 2026-10-24, signed off by Mike in #orion-dev)

## Setup (verified)
- Board `orion` (`~/.hermes/kanban/boards/orion/kanban.db`). Never use `default` for Orion.
- Only one gateway on the host dispatches: whoever holds `~/.hermes/kanban/.dispatcher.lock` (usually the default/Val gateway, pid in claim_lock `uranus:<pid>`). The dispatcher only submits the claim to the assignee profile's own gateway (`kanban_worker_client`), so a raymond card always executes inside raymond's gateway (`owner_admitted.db` = raymond `state.db`).
- `kanban.dispatch_profiles` per home (Mike approved touching the other homes): default=`default,raymond`, gordon=`gordon,raymond`, bones=`bones,raymond`, raymond=`raymond`. raymond must be in every home's list, or raymond cards sit `skipped_nonspawnable` whenever that home holds the lock. Never add another profile to raymond's list.
- `kanban.auto_decompose: false` in all four homes (the decomposer routes triage cards to any profile). Never use `--triage` or `specify` on `orion`.
- raymond `kanban.max_in_progress_per_profile: 1` is NOT enforced when another home holds the dispatcher lock (the cap is read from the dispatching home's config; default home has none). Assigning 3 cards at once (2026-10-24) started all 3 in parallel within 60s. To run one at a time, assign one card and the next only after it finishes, or set the cap in the dispatching home too (needs Mike's OK, other profile).
- Check: `HERMES_HOME=<home> hermes kanban diagnostics | grep dispatch_profiles` for each home.
- A session can leave a duplicate `chat_type=group` subscription on the setup thread `1792854767.962179` (seen 2026-10-24). After every move, run `notify-list` and `notify-unsubscribe` the extras, or the setup thread gets woken alongside the card's own thread and two sessions handle the same event.

## Card recipe
- Body = `~/.hermes/profiles/raymond/workspace/orion/kanban/task-preamble.md` + task section (cat into a body file, `--body-file`).
- `hermes --profile raymond kanban --board orion create "<title>" --body-file <f> --workspace worktree:/home/hermes/git/orion --branch feat/<topic> --skill orion --max-retries 1 --max-runtime <45m..2h> --created-by raymond --json`, created UNASSIGNED (unassigned+ready never dispatches, verified over a full tick).
- Subscribe the orion-dev thread: `notify-subscribe <id> --platform slack --chat-id C0CB8SJKM8C --thread-id <thread ts> --chat-type group --parent-chat-id C0CB8SJKM8C --user-id U0CBKGZFU9E --notifier-profile raymond --delivery-mode notify+wake` (Mike, 2026-10-24). With `--chat-type group` the wake lands in the thread's real session (`slack:group:<team>:<chan>:<ts>`), so it has the thread history. `--chat-type thread` opens a separate `slack:thread:` session with no history (tested). Re-running notify-subscribe on the same key updates the mode/type in place and keeps the cursor.
- Worktree lands at `/home/hermes/git/orion/.worktrees/<task-id>` (`.worktrees/` is in `.git/info/exclude`; vitest `tests/**` and tsc `src,tests` don't see it). It's removed on completion unless dirty/unpushed; the branch stays: delete an empty canary branch with `git branch -d`.

## One thread per card (Mike, 2026-10-24)
- Mike starts each card with a top-level orion-dev message (e.g. "go t_xxx"); my reply threads under it, and that thread (thread ts = his message ts, shown in the session context) is the card's home for questions, blocks and approvals.
- Cards already running when several share a thread: post one root message per card myself (Slack `chat.postMessage` to C0CB8SJKM8C with `SLACK_BOT_TOKEN` read from the profile `.env` in Python, never printed; the returned `ts` is the thread ts). Put status plus any decisions owed in that root message, then move the sub with the recipe above (`--chat-type group`, not `thread`).
- On "go": `notify-unsubscribe <id> --platform slack --chat-id C0CB8SJKM8C --thread-id <setup thread ts>`, `notify-subscribe` the new thread ts (recipe above), `notify-list` to confirm, then `assign <id> raymond`. Post the card's scope + stop point in the thread.
- `--delivery-mode notify` only posts the notifier's text ping in the thread (the sub's `last_ping_event_id` advances; sends are debug-logged only, so gateway.log shows nothing). It does NOT start a turn for me, so I never see a finish or block until Mike writes. `notify+wake` also wakes my session in that thread (log: `kanban notifier: woke agent for <id>`), so I verify the result and report, or bring the block decision, without being asked. That is the standard mode now. On a wake turn, follow the Gates verification below before reporting.
- On completion, the worktree is kept when its branch isn't on the remote (a local-only docs branch counts). After merging and pushing: `git worktree remove .worktrees/<id>`, then `git branch -d <branch>`.
- On a block notice there, read `kanban show <id>` (the block reason + worker summary), verify its claims, and put the decision to Mike in that thread; unblock only on his reply there. `thread_require_mention: false`, so he can reply without tagging.
- Unblock with `unblock <id> --reason "<Mike's picks, one line each> NEXT STEP ONLY: <exact deliverable, path, commit, then kanban_block('<gate text>')>. Build no code in this run."`. The reason is stored as a comment the respawned worker reads, and its own body still says "spec only", so the next step and its stop must be spelled out there.
- The board's block-loop guard routes a card to `triage` on its 2nd block (event `block_loop_detected`, limit 2), e.g. spec gate then plan gate. That is not a failure: verify the worker's output as for any block. With `auto_decompose: false` nothing picks it up. Don't unblock it a third time; take the next step (plan execution) interactively instead.
- Moving a card's work out of kanban (plan execution after Mike's go): `complete` refuses a triage card ("unknown id or terminal state"), so `archive <id>`. Then `git worktree remove .worktrees/<id>` (it holds the branch checked out, so your own `git worktree add $TMPDIR/... <branch>` fails until it is gone) and continue in your worktree; `git rebase main` there first if main moved since the spec branch point (the branch is local-only docs, so it's safe, and the merge stays a fast-forward). The thread subscription can stay; it goes quiet with the archived card.
- The setup thread was `1792854767.962179`; cards created there are subscribed to it until moved.

- A card's second `kanban_block` (spec gate, then plan gate) trips the block-loop limit (2): the card goes to `triage` with a "routed to triage after repeated blocks" notice. That's not a failure; read `show` for the summary. `complete` refuses a triage card ("unknown id or terminal state"); `archive <id>` works. When Mike approves execution, archive the card and run SDD interactively in a `$TMPDIR` worktree (remove the card's `.worktrees/<id>` first so the branch can be checked out), rather than unblocking it a third time.

## Gates
- Mike says "go <id>" / "approved" in orion-dev; I run `assign <id> raymond` or `unblock <id>` and keep that message as the record. Approval covers the next step only.
- Cards end in `kanban_block` at every decision (spec ready, options to pick). Kanban covers scoping, specs and green branches only: merge, live build, live backfill, push, paid analyst runs, config-proposal approvals and cron changes stay interactive under the live-install rules.
- Verify every worker summary yourself before reporting (rerun its tests in your own `git worktree add --detach $TMPDIR/... main`, diff live HEAD/status/`orion.db`+`.env` mtimes/`dist` against a pre-snapshot). The canary's summary checked out exactly (100 files / 1127 tests).
- Headless workers are refused `rm -rf`; the preamble tells them to use `shutil.rmtree`. Keep that guard; don't loosen approvals.
- Headless workers are also refused `execute_code`, and any terminal command whose text contains the string `rm -rf`, even inside a grep pattern. For a DB or transcript analysis, write a `.py` file under `$TMPDIR` with write_file and run it with `python3 <file>` in the terminal; open the live DB read-only via `sqlite3.connect('file:...orion.db?mode=ro', uri=True)`.
