# Provisioning scripts Mike runs (dev host, Orion server)

Raymond writes host setup as scripts in `scripts/provision/` (`dev-postgres.sh`, `orion-host.sh`, `sql/*.sql`, `files/*`, `test/run.sh`, README). Mike runs them as root. Raymond never runs them for real: he has no sudo, and the server isn't reachable before the deploy keys exist.

## Writing them
- Plain bash with `set -euo pipefail`. Every change goes through a `run`/`write_file` helper that prints instead of acting under `--dry-run`, and skips with an `ok:` line when the state already holds. A second run prints only `ok:` lines.
- `--dry-run` must work as non-root and list every change a real run makes.
- Every refusal (wrong OS codename, SSH caller not in `--ssh-from`, non-empty target dir) happens before any change.
- Finish with a `SELF-CHECK: N passed, M failed` block, and print public keys as `pubkey:` lines. Mike pastes both back.
- Never print secrets. Never overwrite a filled `.env`, a generated key, or a config file whose placeholders have been filled.
- Pin version-sensitive software to upstream, not the Ubuntu archive: PGDG for Postgres and pgBackRest, so both hosts run the same minor; the official Node tarball with its sha256; yt-dlp from pip. Then a newer server OS than dev's is no blocker. Check each package's version in both codenames' apt indexes (`dists/<codename>-pgdg/main/binary-amd64/Packages.gz`).
- Put data on the big partition with the tool's own option, never a symlink. For Postgres, `--pg-datadir`: `pg_dropcluster --stop` plus `pg_createcluster -d <dir>`, only when the package-default cluster is fresh. Symlinks under `/var/lib/postgresql` break on upgrades and with AppArmor. Ask for `lsblk` and `df -h` before choosing paths: a small `/` means everything that grows (data dir, dumps, refresh drops) goes under the large mount.
- A local backup repo on the same physical disk as the data gives no disk-failure protection. Say so, and keep off-box (Spaces) as the real copy.

## Testing without root
- `test/run.sh`: dry runs of each script, refusal cases, and helper unit tests. Run it with `SHELLCHECK=<path>`. shellcheck can be installed without root via `pip install --target <dir> shellcheck-py`.
- SQL leg: set `PG_BINDIR` (the installed `/usr/lib/postgresql/18/bin`, or binaries unpacked from the PGDG .debs). It runs the role SQL twice against a throwaway `initdb` cluster owned by `hermes`.
- Before comparing test counts, run the base commit with the SAME `SHELLCHECK`, for example in an existing detached `.worktrees/proof-<sha>`. A run without shellcheck shows one FAIL and fewer PASS lines, so it is not a valid baseline.
- Prove systemd semantics (`ExecStopPost` env such as `SERVICE_RESULT`, `%n` specifiers, whether a hook changes the unit's `Result`) with a throwaway user unit file in `~/.config/systemd/user/` plus a fake binary on `PATH`. Run `systemctl --user daemon-reload` and `start`, read `show -p Result`, then remove the unit. Use a unit file, not `systemd-run -p`, because transient properties don't expand specifiers like `%n`, so the result is misleading.
- The harness must fake the system probes (`dpkg-query`, `pg_lsclusters`, `psql`, `/etc/postgresql` via a test hook). Without fakes, dry runs read the dev host's real packages once Postgres is installed there, and the tests fail.

## Enabling backups (`orion-host.sh --enable-backups`)
- Off-box repo = DigitalOcean Spaces (S3-compatible object storage on Mike's existing DO account, about $5/month flat). Explain it in those terms when he asks; Backblaze B2 / Cloudflare R2 work too but are a new account plus config change.
- Mike's steps, in order: create bucket + an access key scoped to it; fill every `REPLACE_ME` in `/etc/pgbackrest/pgbackrest.conf` (endpoint, region, bucket, key id/secret, a long random `repo1-cipher-pass`); `age-keygen -o orion-dumps.key` on HIS machine (private key never on venus/uranus); then re-run `orion-host.sh` with the usual flags plus `--enable-backups --dump-recipient age1...`. Put both new flags in the command you give him: `--enable-backups` refuses without a recipient until one is stored in `/etc/orion/dump-recipient` (later runs can drop `--dump-recipient`).
- `repo1-s3-endpoint` is the region host only (`sfo3.digitaloceanspaces.com`). With `repo1-s3-uri-style=host` pgBackRest prefixes the bucket itself, so the bucket URL the DO console shows (`<bucket>.sfo3.digitaloceanspaces.com`) as endpoint addresses a host that doesn't exist and `pgbackrest check` fails (seen as `[095] unable to load info file .../archive.info`). After fixing it, re-run the script (it runs `stanza-create` then `check`), or by hand `sudo -u postgres pgbackrest --stanza=orion stanza-create && ... check`.
- The first enable turns on `archive_mode`, which restarts Postgres once: tell Mike before he runs it, keep it clear of the staging/prod nightly slots, and check `ssh orion-stage status` (heartbeat, logs) afterwards.
- **Backups dead-man ping** (`fix/backup-deadman`): before it, nothing pinged the healthchecks `backups` check, so an unpaused check alerted daily while every backup succeeded. Each backup unit runs `/usr/local/sbin/orion-backup-ping` (`files/orion-backup-ping`) from `ExecStopPost` with `SERVICE_RESULT`. full/diff send `report` (ping on success, `<url>/fail` otherwise); `orion-pg-dump` sends `fail-only`, because its 08:30 run comes before the check's 09:00 slot. The URL comes from `--backup-deadman-url-file <f>` (a file keeps it out of ps and shell history) and is stored in `/etc/orion/backup-deadman-url` (root:postgres 640), written `quiet` so a dry run never prints it. The script always exits 0, so a failed ping never fails a backup. Mike's test after the re-run: unpause the check, then `systemctl start orion-backup-diff.service`.
- **Triage of a backup/healthcheck alert:** first read the provisioning code to see what is supposed to ping the check. Raymond can't see systemd or Spaces on venus (forced command, no backup verb), so ask Mike to run these as root and paste the output: `systemctl list-timers 'orion-*'`, `systemctl status orion-backup-{diff,full} orion-pg-dump --no-pager | grep -E 'Active|code='`, `sudo -u postgres pgbackrest --stanza=orion info`, `ls -l /home/orion-backups/dumps/prod/YYYY/MM/`. Read the results like this:
  - The first full backup lands on whichever diff/full run comes first, because pgBackRest promotes a diff to a full when no full exists.
  - A tiny prod dump from before the prod load is expected.
  - `orion-pg-dump` exits 1 if either env's Spaces upload fails, so exit 0 proves off-box copies for both envs.
  - "Unit changed on disk, run daemon-reload" is harmless if `systemctl cat` matches what `orion-host.sh` writes and shows no drop-ins; the next re-run that changes the units reloads systemd.
  - A restore drill is a separate open item: a healthy `pgbackrest info` does not prove the backups restore.
- When he pastes `SELF-CHECK: N passed, 1 failed` without detail, ask for the `FAIL:` line and the lines after it before guessing.

## Deploy keys and snapshot repos (after the server run)
- Create the per-env deploy keys on uranus only on Mike's go: `ssh-keygen -t ed25519 -N '' -f ~/.ssh/orion-<env>_ed25519`, never overwriting an existing file. Post the public halves as `echo '<key>' > /tmp/deploy-<env>.pub` lines plus the full re-run command with `--deploy-key-stage/--deploy-key-prod`.
- Verify each key yourself, including the refusal of shell input: `ssh -o BatchMode=yes -o IdentitiesOnly=yes -o StrictHostKeyChecking=accept-new -i ~/.ssh/orion-<env>_ed25519 orion-<env>@<server> status`, then the same with `'id; cat .env'`. The second must be refused by `orion-remote`.
- Forced-command keys block `scp`, so deploys stream the tarball over the SSH session's stdin.
- A forced-command verb must never pass caller text to a tool that has its own escape language. `psql -c`, `-f` and stdin all run backslash meta-commands, and `\!` is a shell, so a "read-only SQL" verb built on psql gives the key a shell and `.env`. Run such queries through Orion's own driver (`orion db query-ro`): log in as a SELECT-only role, in a READ ONLY transaction with a statement timeout, and refuse any backslash and a second statement. Test it with a real psql reproduction of the escape, which must fail before the fix and pass after.
- Third-party trust anchors that a script or implementer embeds (GitHub's SSH host keys for the publisher's `known_hosts`) come from the authoritative endpoint (`curl -s https://api.github.com/meta`, `ssh_keys`), fetched by you and pasted into the dispatch verbatim. Never write them from memory, and never let a subagent guess them. With the keys pinned, the publisher uses `StrictHostKeyChecking=yes`, not `accept-new`.
- Snapshot repos (one per env): private, created EMPTY (no README, licence or .gitignore, because the publisher makes the first commit and alerts on any commit it didn't write), default branch `main`, no branch protection. Each gets its env's server publish key as a deploy key with write access.
- A personal-account GitHub repo has no read-only collaborator role: inviting `retrobitbot` always grants write. Accept invitations with `PATCH /user/repository_invitations/<id>` using GH_PAT. If Mike wants read-only, offer a read-only deploy key from uranus instead of the collaborator.
