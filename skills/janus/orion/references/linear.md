# Orion project management in Linear (Mike, 2026-11-16)

Linear is the project board for Orion. Workspace "Retrograde Capital", team `RET`, project `orion`.

## Rules (Mike)
- One parent issue per phase; one sub-issue per step/sub-task inside it (nesting allowed, e.g. R2 -> its rollout steps).
- Anything that needs Mike to act (a decision, a go, a sudo step, a sign-off) gets the `Blocked` label. Remove it once he has done his part.
- Status: `Todo` until I start it -> `In Progress` -> `Done`. Don't use Backlog/In Review for phase/step tickets. Exception: under the Build-with-Hermes flow the `T<n>` task sub-tickets move through In Review via `linear_task_state` (`in_progress` at implementer dispatch, `in_review` at review dispatch, back to `in_progress` plus a findings comment for a fix round, `done` with a summary: commits, suite count, review verdict, fix rounds, deferred minors as a `- [ ]` checklist).
- New phases/steps/decisions that come up go into Linear as they appear; keep descriptions short with doc/branch/tag refs.

## Working a release ticket from a Linear session
- On the first turn: move the ticket to `In Progress` (`linear_issue_update` state, session scope, no approval), then follow the main skill's release procedure (fresh prod pull read-only, `BRIEF.md` + parallel scoping subagents, plan with priced decisions, `Blocked` at the gate). Scoping subagents run in the background: end the turn with a short status of what is running and which decisions the plan will ask for; their results arrive as a later turn.
- "Build with Hermes" in a thread comment (not only in the ticket description) means: switch that ticket to the `linear:manage-superpowers` flow. Load it and do its Setup before more stage work. The Orion project already carries a `Repo` link (`https://github.com/masha256/orion`), which is the repo candidate; the repo has no `.hermes-linear.yaml` until that setup commits one. Each setup question is one `clarify` select; an `outcome: pending` ends the turn.
- Under that flow the open release decisions (e.g. what a revenue line means, chain coverage, booking of a subsidy, pricing method, short-history labelling) are asked in the thread one `clarify` select at a time, each priced from the scoping measurements with the recommendation first; a timed-out select stays open in the thread, so end the turn with a status listing the queued questions. Then present the design in 3-4 sections (architecture, statement/config, history+errors, testing+rollout), one approval select each, correcting any earlier section in the next one's text when you find a flaw.
- A release that adds a new source class (a new adapter family, new chains, a revenue redefinition) gets its own short release spec under the flow (`docs/superpowers/specs/<date>-orion-phase<N>-r<M>-<topic>-design.md`, `Linear: <ID>` header, decision table, a line saying which phase-spec text it supersedes, full addresses), committed, pushed and `linear_sync_spec`'d, then a review select; the plan follows only after that approval. A release that only executes the phase spec as written goes straight to the plan.
- Gates under the flow are `clarify` selects: the plugin sets and clears `Blocked` for a pending select itself, so don't also add the label by hand (it then stays after the answer until removed).
- Map Orion's conventions onto that flow rather than replacing them: the per-release plan keeps `### Task N:` headings and a `Linear: <ID>` header (`linear_sync_plan` creates the `T<n>` sub-tickets and writes their IDs into the headings: commit that change), and Orion's own gates (stage -> soak -> prod on Mike's go, byte-identical proof for untouched assets) still apply; the flow's "open the PR, never merge" finish does not authorise any deploy. Plan-text changes from the SDD pre-flight rulings are committed and re-synced before Task 1's dispatch. A ruling made mid-build that changes designed behaviour (e.g. making a report guard opt-in) amends BOTH the spec and the plan in one commit, then `linear_sync_spec` and `linear_sync_plan` again with summaries that mention the change, before the affected task is re-dispatched (regenerate its brief from the amended plan).
- A release that adds an on-chain revenue source (multi-chain fee scans, incentives, on-chain pricing): read `references/onchain-revenue-scans.md` before scoping; it holds the chain-probe recipe, method rules and the Orion code seams that break.
- Under SDD on Hermes: resume an implementer for fix rounds 1-3 with `delegate_task(action='continue', subagent_id=<implementer id>)`; dispatch reviewers by pointing them at the skill's `task-reviewer-prompt.md` / `re-review-prompt.md` with the brief, report, diff-file and constraint values filled in, writing their review to a file in the plan workspace. `delegate_task` has no per-dispatch model choice, so every seat runs the session model.
