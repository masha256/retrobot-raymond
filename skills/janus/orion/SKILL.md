# Orion operations and development

This skill covers Mike's orion valuation pipeline (VVV/HYPE/AERO/CRV/yCRV/cvxCRV/sdCRV/UNI/CAKE/LIT/LINK/SKY/PUMP live; PUMP is on Solana; LINK is the first buy-and-hold asset; yCRV/cvxCRV/sdCRV are CRV liquid-locker wrappers): diagnosing ingest failures, vetting or swapping data endpoints and API keys, running the test suite, onboarding and calibrating new assets. Mike manages orion development from the Raymond bot's orion-dev topic.

Holder yield / growth / revenue reporting: see `references/holder-yield-report.md`.
Price-driver questions, explaining a price-vs-target gap, and new valuation ideas (TVL/TVS, network effects, capture options): see `references/price-drivers-and-valuation-gaps.md`.

## Repairing bad rows a live run wrote
- Fix the code on a `fix/<topic>` branch with a regression test first. Then list the exact rows the run left (`signals`, `valuation_runs`, `snapshots`, `config_versions.created_at`; find them by scanning `*_at`/`as_of` columns for dates past today).
- Propose the repair to Mike before running it, in this order: deploy the fix (ff-merge + build); fresh backup; one `BEGIN…COMMIT` whose `DELETE`/`UPDATE`s are each pinned by id AND asset (AND signal_id/hash where there is one); re-run the valuation without a fetch or the agent.
- Leave correct observations and journal rows in place. Don't edit the append-only `signals.jsonl`/`ticks.jsonl` logs.
- `PRAGMA foreign_keys` is off in `orion.db`, so delete children before parents (signals → valuation_runs → snapshots) by hand.

## Changing the live install (Mike's standing rules)
The repo working tree IS the live site: cron runs `run-daily.sh` → `dist/cli/index.js` with `ORION_HOME` = repo root, so `orion.db` and `.env` there are production.
1. Before any live write, check nothing is mid-run (`pgrep -af 'dist/cli/index.js|run-daily' | grep -v pgrep | grep -v tirith`; a bare `orion` pattern matches the tirith security scanner's own command line and aborts the job) and note when the next cron tick fires.
2. Back up the DB first, with the sqlite online backup, then verify it: `sqlite3 orion.db ".backup 'backups/orion.db.pre-<topic>-<UTCstamp>'"`, `PRAGMA integrity_check` on the copy, and compare row counts (observations, assumption_sets, fetch_runs, anomalies). `chmod 600` the copy and keep `backups/` out of git via `.git/info/exclude`.
3. Before merging a change that must not move targets, save a baseline with the OLD dist on live: `model whatif <a> --as-of <fixed ISO> --json > base/<a>.json` for all assets (read-only). Merge with `git merge --ff-only feat/<x>`, then `npm run build` — cron runs `dist/`, so an unbuilt merge changes nothing live — then `asset validate` every asset with the built CLI, not only the new one. Re-run the same whatif with the new dist and `cmp` each file; report identical/differs per asset.
   - **Migrations apply on the first command that opens the DB; `asset validate` does not.** Run a read command (e.g. `data anomalies --all`), then confirm `select max(id) from schema_migrations`, that a rebuilt table kept its rows, `sqlite_sequence` and indexes, and `PRAGMA integrity_check` / `foreign_key_check`.
   - **Re-do on live every data entry you made only in scratch** (manual disclosures via `data set ... --citation --quote`, first fetch of a new metric with `data fetch <a> --metric <key>`). List them in the build report so none is forgotten at merge.
4. Run live commands with `node dist/cli/index.js ...` (what cron uses, not `tsx src`), and in the reply list every command run against live verbatim, in order, each with its result, and say plainly which ones wrote to the DB. Record row counts before and after, and state that a dry run left them unchanged.
5. Before a step that calls the analyst agent (a tick or bootstrap, which costs Anthropic spend) or writes signals, say what it will write and ask for a go.
6. Before a long live backfill, rerun the full suite on the final commits, and rehearse the exact live command in a scratch home for timing and anomalies; scope it with `--metric` to the new series (see `references/data-sourcing-and-protocol-revenue.md`). Start it clear of the nightly cron window and the per-asset lock.
7. Do dry runs and calibration during development from a throwaway home instead (`ORION_HOME=$TMPDIR/<x>`). Seed it with assets and `.env`, plus a `.backup` copy of `orion.db` when you need live history. It never touches production. Delete it afterwards, because it holds a copy of `.env`.
- A reported number that contradicts the protocol's known mechanics (e.g. protocol income on a token that pays ~100% to holders) is a data-integrity signal: compare the stored rows against the source today before explaining it. A source-side revision is likely, and the same series often feeds the valuation, so report the valuation impact too.
- Push only as described in "Pushing to GitHub" above. Never report a push you didn't see succeed (re-fetch and confirm `origin/main` = local). If `origin/main` has moved without you pushing, check `git reflog show --date=iso origin/main` and tell Mike when it moved; don't assume who did it.
- After re-fetching or correcting a flow that feeds a `derived` metric (e.g. HYPE `revenue_run_rate_usd` = `flow_annualized(flow_usd.af_buyback)`), include the derived key in the same fetch (`--metric <flow> --metric <derived>`) before `model run`. A `--metric` fetch of only the flow leaves the stored derived value stale, so the valuation emits a no-change signal that stays in history.
- `package-lock.json` is committed; a later npm-touched lock change is again an unrelated working-tree change: leave it and mention it.

## Answer style
- Mike asks for short, succinct answers when aligning on definitions: give the answer and the numbers, skip background and "how it works". Bullets per asset, a one-line recommendation, then the question he owes. Long explanations cost him attention. When he asks to "define X vs Y", answer in two bolded one-to-two-sentence definitions plus one line applying them to the asset at hand (standard wording for recurring terms lives in `references/definitions.md`).
- When he says prod is mid-change ("wait until I say"), do nothing that reads or writes it; scratch-only or read-only chain work is fine, and say so.
- When he reviews items one by one (e.g. each asset's revenue definition) and says "save for dev", append the finding to `~/.hermes/profiles/raymond/workspace/orion/dev-queue-revenue.md` (finding, numbers, sources, proposed design) and move on to the next item. Build nothing until the whole batch is reviewed.
- When Mike proposes a valuation idea (e.g. TVL or value secured as a value driver), don't answer "wrong metric" and move on. Name the economic mechanism he means, show where it fits the model without double-counting (growth, durability, capture probability), test it with data, and offer priced build options. He pushes back on dismissals that are too academic. When he says a metric should be part of the "value", he means an input somewhere in the valuation algorithm, not a separate addend. Map it to the specific assumption keys it would move, and state plainly which ones the evidence supports.
- He prefers generic mechanisms over special cases: propose config-driven designs (a stream list with a settlement mode), not a bespoke series per new source.
- For any rate- or fee-dependent stream, read the parameter from the protocol itself daily (and store it, with the counterparties' addresses) rather than a fixed % or market proxy, so manager/fee/methodology changes surface automatically; alert on changes.
- When he asks for an orion-dev prompt: one code block that points to the queue file for figures and sources, then numbered Do items, Constraints (targets unchanged; scratch `ORION_HOME` until verified), and Verify (tests green, targets byte-identical, the expected report numbers, show the table, "Commit; don't push"). Say any threshold you picked for him outside the block.

When it is unset, orion falls back to `https://mainnet.base.org` (`DEFAULT_RPC_URLS` in `src/ingest/run.ts`). They also use CoinGecko, DefiLlama and `http_json` cross-checks.
- **Ethereum mainnet (chain 1)**: `ORION_ETH_RPC_URL` in `.env` holds Mike's Alchemy key (passes 100k-block `eth_getLogs` with `blockTimestamp`, and archive `eth_call`). Free mainnet RPCs (drpc, publicnode) refuse ranged logs beyond ~10k blocks and archive reads, so never default chain 1 to a keyless URL. Chains live in `src/ingest/transport/chains.ts` (per-chain log range, block time, keyless default or none); adding a chain = a row there plus the viem chain in `viemRpc.ts`. The transfer scanner reads one day per `eth_getLogs` call regardless of the range cap, so a backfill costs one call per day (~2 min for 100 days on mainnet).
- **HYPE**: no RPC. It uses `api.hyperliquid.xyz/info` (REST), CoinGecko and DefiLlama.
- **CoinGecko**: the optional `COINGECKO_API_KEY` is sent as the demo-key header. Without it, the code spaces requests 2.5s apart to stay under the keyless limit.
- To re-derive this list: `grep -n '^ingest:' assets/*.yaml` and `grep -rn 'env\.\|https://' src/ingest`.

## Re-running ticks after an outage
- Orion has no once-per-day guard: a second tick re-fetches and writes a new latest signal; the bad partial rows stay in history (fine). The agent runs only if cadence/triggers say so.
- COINGECKO_API_KEY is unset (keyless, spacing is per-process), so never fire ticks in parallel. Run a background script that calls `hermes --profile raymond cron run <job_id>` per asset, 5 min apart (each call blocks until that run finishes and delivers). Verify per job: newest cron/output file shows `"ingest":{..."outcome":"ok","sources_failed":[]}`, and jobs.json `last_status` ok with no `last_delivery_error`.

## Diagnosing ingest failures
The cron output .md files rarely contain the real error. Query `fetch_runs` instead. Its columns are `id, asset_id, started_at, ended_at, outcome, detail_json`; outcome is `ok` or `partial`. Per-source errors live in `detail_json.sources[]`:
```
sqlite3 orion.db "select f.asset_id,f.started_at,json_extract(s.value,'$.sourceId'),substr(json_extract(s.value,'$.error'),1,250) from fetch_runs f, json_each(f.detail_json,'$.sources') s where json_extract(s.value,'$.status')!='ok' order by f.id desc limit 20;"
```
- "RPC Request failed." on `chain_levels`, on `adapter:*` `totalSupply()`, or on `transfer_flow` `eth_getLogs` means the Base RPC was throttled or rejected the request. Errors are deliberately scrubbed: viem's `shortMessage` is used and URLs are cut to their origin. To see the provider's actual message, curl the endpoint directly.

## Outage-hit ticks and same-day re-runs
- During a network outage a tick still exits 0 with `outcome: completed`, but `ingest.outcome` is `partial` and `sources_failed` lists the CoinGecko, DefiLlama and chain sources that failed. The signal written from that data is mostly stale: look for `target_delta_pct` 0. Judge each tick by `ingest.outcome` and its failed-source count, not by the tick outcome or the cron status. A cron run can be marked error only because the report agent or Telegram failed after the tick finished.
- A second tick on the same day is safe. `tick` has no once-a-day guard: it fetches again, writes a new signal that becomes the latest, and leaves the earlier rows in history. The analyst agent runs only if `dueRunType`/triggers call for it, so if the morning report showed `agent: null` and `agent_would_run: null`, a re-run costs no agent spend.
- To repair a morning of bad ticks, re-fire the asset cron jobs one at a time, 5 minutes apart (the procedure is in `cron-job-administration`, "Auditing whether jobs ran"). Don't fire them in parallel: without `COINGECKO_API_KEY`, the 2.5s request spacing works only inside one process, so parallel ticks get throttled and fail again. Confirm the first re-run shows `ingest.outcome: ok` and no delivery error before you tell Mike the batch is working.

## Vetting a new RPC endpoint (before relying on it)
Orion's Base RPC must support all of the following. Test every item. A provider that passes the reads can still fail the logs check.
1. `eth_blockNumber` and `eth_getBlockByNumber` (historical): used for the block-by-time search.
2. `eth_call` at a specific block through Multicall3. All reads go out as one batched call.
3. **`eth_getLogs` over a 2,000-block range** (`MAX_LOG_RANGE` in `src/ingest/transport/rpc.ts`). Free tiers often cap this hard; Alchemy Free allows only **10 blocks** and returns `-32600 "Under the Free tier plan..."`. Viem surfaces that as the misleading "JSON is not a valid request object." Probe the range with raw curl at spans 10, 11, 500 and 2000 to find the cap.
4. **`blockTimestamp` on every log**. This field is non-standard, and orion throws when it is missing. Check with a small-range `eth_getLogs` on the VVV token's Transfer topic. Burns to the zero address are sparse, so use plain transfers rather than burns as the sample.

Procedure:
- Append the URL to `.env` (it is gitignored). Then run a throwaway `.mjs` probe that imports the built transport, `dist/ingest/transport/viemRpc.js` (`createViemRpc`) and `rpc.js` (`getLogsChunked`). That exercises the exact code path the cron jobs use. Include the historical range that last failed in `fetch_runs`, plus one full day of back-to-back chunks (~22 for Base).
- Pipe every output through `sed -E 's#/v2/[A-Za-z0-9_-]+#/v2/***#g'` (or an equivalent for the provider's path), because keyed URLs must not land in logs or chat. Delete the probe file afterwards.
- If any check fails, **comment the line out** in `.env` with a one-line reason and the fix (for example, "uncomment after PAYG upgrade"). Then confirm with `grep -c '^ORION_BASE_RPC_URL=' .env` that it is 0. A rejected endpoint is worse than the public fallback, and the next nightly run would hit it.
- **Plan-tier changes take effect gradually.** Right after a Free→PAYG upgrade, the same key answers some requests under the new limits and others under the old 10-block cap, whatever the span. So one passing 2,000-block request proves nothing. Run several rounds of mixed spans (10/11/50/500/2000, with and without the Transfer-to-0x0 topic filter) and enable the key only on a 100% pass. A new key from the same account inherits the account's tier, so swapping keys does not get around a cap.
- For a deferred retest, use the profile script `scripts/orion-rpc-retest.sh` (it wraps `orion-rpc-retest.mjs`). It runs 36 raw range probes plus orion's transport (latest block, multicall, and 7 days of chunked burn logs, about 150 chunks). It uncomments `ORION_BASE_RPC_URL` only if every check passes, and prints a key-masked report. Schedule it as a one-shot `no_agent` cron job delivering to orion-ops; dry-run it by hand first. Before enabling a different provider, change the line it matches (`/v2/` masking, `# DISABLED` comment).
- Report the result as a pass/fail per check. Quote the provider's own error text and give the concrete options (upgrade the plan, switch provider, or shrink the chunk size, which costs ~200x more calls).

Volume, for sizing plans: ~22 `eth_getLogs` calls a day, a few multicalls, and ~2k calls for a one-time 90-day backfill. That is free-tier volume. A paid plan only buys range limits and throttling headroom.
