# Orion operations and development

This skill covers Mike's orion valuation pipeline (VVV/HYPE/AERO/CRV/yCRV/cvxCRV/sdCRV/UNI/CAKE/LIT/LINK/SKY/PUMP live; PUMP is on Solana; LINK is the first buy-and-hold asset; yCRV/cvxCRV/sdCRV are CRV liquid-locker wrappers): diagnosing ingest failures, vetting or swapping data endpoints and API keys, running the test suite, onboarding and calibrating new assets. Mike manages orion development from the Raymond bot's orion-dev topic.

Holder yield / growth / revenue reporting: see `references/holder-yield-report.md`.
Price-driver questions, explaining a price-vs-target gap, and new valuation ideas (TVL/TVS, network effects, capture options): see `references/price-drivers-and-valuation-gaps.md`.

## Direction (Mike, 2026-10-27): Orion = data core for coinrevs
- Planned, not yet specced: remove the price-target/valuation layer (engine, drivers, signals, analyst runs; any future valuation is a separate project on Orion data) and remove **every** DefiLlama dependency, cross-checks included; this supersedes the 2026-10-11 DefiLlama rule below once built. Comparison with DefiLlama/Token Terminal/Artemis moves to a separate internal tool. Open decisions at that point: archive vs delete DefiLlama-sourced history, keep/retire the disclosure watcher, CoinGecko licence, phase order, builder/partner fees inside revenue, wrapper revenue treatment, labelled derived gross-ups.
- Revenue becomes gross user-paid fees with a cost-of-revenue line (see `references/exec-summary-and-comparison.md`).
- Mike wants no chain indexer if at all possible. Method ladder: contract state reads > single-address log scans / first-party API > fixed pool-list scans with stated coverage > licensed query engine. Model multi-version protocols (UNI v2/v3/v4/Unichain) as summed streams.

Dune is "internal use only" below Enterprise. Check any vendor's commercial terms (CoinGecko, RPC provider, others) before the site relies on it.

- **Approving a config proposal** (`model proposals approve <id>`) edits `assets/<a>.yaml` in the live tree in place, and LIT-style hash pins in tests then go red on `main`. Procedure: rehearse the approve on a scratch `.backup` home to capture the exact YAML; build a `fix/<topic>` branch whose first commit is that YAML byte-for-byte, then comments, persona text and every hash re-pin (`grep -rl <old hash> tests`), suite green. On live: backup, whatif baselines, approve, check `git diff` equals the branch's first commit, `git checkout -- assets/<a>.yaml`, `git merge --ff-only`, build, validate, compare whatif, re-fetch the metric, push. A replay fixture that ran against the pre-approval config (e.g. the Q3 disclosure e2e) must keep using that config, not be regenerated.
- Before removing a feature worktree, copy the SDD ledger's `minor (deferred)` and `Ruling:` lines into the committed followups note or the dev queue: the ledger lives in the worktree's git-ignored `.superpowers/` and is deleted with it.

## Repairing bad rows a live run wrote
- Fix the code on a `fix/<topic>` branch with a regression test first. Then list the exact rows the run left (`signals`, `valuation_runs`, `snapshots`, `config_versions.created_at`; find them by scanning `*_at`/`as_of` columns for dates past today).

## Re-running ticks after an outage
- Orion has no once-per-day guard: a second tick re-fetches and writes a new latest signal; the bad partial rows stay in history (fine). The agent runs only if cadence/triggers say so.
- COINGECKO_API_KEY is unset (keyless, spacing is per-process), so never fire ticks in parallel. Run a background script that calls `hermes --profile raymond cron run <job_id>` per asset, 5 min apart (each call blocks until that run finishes and delivers). ## Diagnosing ingest failures
The cron output .md files rarely contain the real error. Query `fetch_runs` instead. Its columns are `id, asset_id, started_at, ended_at, outcome, detail_json`; outcome is `ok` or `partial`. Per-source errors live in `detail_json.sources[]`:
```
sqlite3 orion.db "select f.asset_id,f.started_at,json_extract(s.value,'$.sourceId'),substr(json_extract(s.value,'$.error'),1,250) from fetch_runs f, json_each(f.detail_json,'$.sources') s where json_extract(s.value,'$.status')!='ok' order by f.id desc limit 20;"
```
- "RPC Request failed." on `chain_levels`, on `adapter:*` `totalSupply()`, or on `transfer_flow` `eth_getLogs` means the Base RPC was throttled or rejected the request. Errors are deliberately scrubbed: viem's `shortMessage` is used and URLs are cut to their origin. To see the provider's actual message, curl the endpoint directly.

## Diagnosing an analyst run that ended `budget_exhausted` (or "should we raise the budget?")
1. `select id,asset_id,run_type,outcome,requests,input_tokens,cache_read_tokens,cache_write_tokens,output_tokens,web_searches,web_fetches,error from agent_runs where asset_id='<a>' order by id` (read-only). The input cap counts weighted units summed over requests (`inputUnitsTenths` in `src/config/agentPolicy.ts`: uncached x1, cache write x1.25, cache read x0.1, integer tenths; YAML key still `input_tokens`). The `agent_runs` columns stay raw tokens, so compute units yourself (`input + 1.25*cache_write + 0.1*cache_read`) before judging headroom. Runs before main 4a2f126 were capped on the raw sum, which is why re-read-heavy runs (#17, #31, #44) stopped at 30-48% of today's units. Compare with the asset's earlier runs of the same type.
2. Check the cap that applied: the per-type defaults are in `agentPolicy.ts`, and `assets/<a>.yaml` `agent.budgets` overrides them per run type. Most assets override only `weekly`, so deep and triage runs use the defaults.
3. Find what filled the context: `agent_transcripts.messages_json` is a dict (`system`, `tools`, `messages`, `responses`). Print each content block's type and `len(json.dumps(block))`, plus each tool_use input. Web search results (~20k chars each) and large web fetches (GitHub PRs, raw API JSON) are the usual culprits.
4. Read `agent_runs.summary_json` `staged` (and `reserve`, present when the run got its one last journal-only request after a cap). A run that ran out of budget commits nothing, so report the change it staged and then lost (key, old→new, whatif target move) along with its evidence.
5. Name the root cause before recommending a bigger budget. If the analyst was researching an unmodelled protocol event (a merger or migration), more budget only pays for re-researching it on every run; the fix is the model rebuild. A failed attempt still resets the cadence (`dueRunType` counts attempts), so say when the next run of that type is due and what cap it has.
6. Give priced options: a per-asset `agent.budgets.<type>` override (moves the config hash: re-pin the asset test, and the next signal lists "config"), bring the rebuild forward, or wait. Give a rough cost estimate per run and label it as an estimate.

## Outage-hit ticks and same-day re-runs
- During a network outage a tick still exits 0 with `outcome: completed`, but `ingest.outcome` is `partial` and `sources_failed` lists the CoinGecko, DefiLlama and chain sources that failed. The signal written from that data is mostly stale: look for `target_delta_pct` 0. Judge each tick by `ingest.outcome` and its failed-source count, not by the tick outcome or the cron status. A cron run can be marked error only because the report agent or Telegram failed after the tick finished.
- A second tick on the same day is safe. `tick` has no once-a-day guard: it fetches again, writes a new signal that becomes the latest, and leaves the earlier rows in history. The analyst agent runs only if `dueRunType`/triggers call for it, so if the morning report showed `agent: null` and `agent_would_run: null`, a re-run costs no agent spend.
- To repair a morning of bad ticks, re-fire the asset cron jobs one at a time, 5 minutes apart (the procedure is in `cron-job-administration`, "Auditing whether jobs ran"). Don't fire them in parallel: without `COINGECKO_API_KEY`, the 2.5s request spacing works only inside one process, so parallel ticks get throttled and fail again. Confirm the first re-run shows `ingest.outcome: ok` and no delivery error before you tell Mike the batch is working.

## Vetting a new RPC endpoint (before relying on it)
Orion's Base RPC must support all of the following. Test every item. A provider that passes the reads can still fail the logs check.
1. `eth_blockNumber` and `eth_getBlockByNumber` (historical): used for the block-by-time search.
2. `eth_call` at a specific block through Multicall3. All reads go out as one batched call.
3. **`eth_getLogs` over a 2,000-block range** (`MAX_LOG_RANGE` in `src/ingest/transport/rpc.ts`). Free tiers often cap this hard; Alchemy Free allows only **10 blocks** and returns `-32600 "Under the Free tier plan..."`. Viem surfaces that as the misleading "JSON is not a valid request object." Probe the range with raw curl at spans 10, 11, 500 and 2000 to find the cap.
4. **`blockTimestamp` on every log**. This field is non-standard, and orion throws when it is missing. Check with a small-range `eth_getLogs` on the VVV token's Transfer topic. Burns to the zero address are sparse, so use plain transfers rather than burns as the sample.

Procedure:
- Append the URL to `.env` (it is gitignored). Then run a throwaway `.mjs` probe that imports the built transport, `dist/ingest/transport/viemRpc.js` (`createViemRpc`) and `rpc.js` (`getLogsChunked`). That exercises the exact code path the cron jobs use. Include the historical range that last failed in `fetch_runs`, plus one full day of back-to-back chunks (~22 for Base).
- Pipe every output through `sed -E 's#/v2/[A-Za-z0-9_-]+#/v2/***#g'` (or an equivalent for the provider's path), because keyed URLs must not land in logs or chat. Delete the probe file afterwards.
- If any check fails, **comment the line out** in `.env` with a one-line reason and the fix (for example, "uncomment after PAYG upgrade"). Then confirm with `grep -c '^ORION_BASE_RPC_URL=' .env` that it is 0. A rejected endpoint is worse than the public fallback, and the next nightly run would hit it.
- **Plan-tier changes take effect gradually.** Right after a Free→PAYG upgrade, the same key answers some requests under the new limits and others under the old 10-block cap, whatever the span. So one passing 2,000-block request proves nothing. Run several rounds of mixed spans (10/11/50/500/2000, with and without the Transfer-to-0x0 topic filter) and enable the key only on a 100% pass. A new key from the same account inherits the account's tier, so swapping keys does not get around a cap.
- For a deferred retest, use the profile script `scripts/orion-rpc-retest.sh` (it wraps `orion-rpc-retest.mjs`). It runs 36 raw range probes plus orion's transport (latest block, multicall, and 7 days of chunked burn logs, about 150 chunks). It uncomments `ORION_BASE_RPC_URL` only if every check passes, and prints a key-masked report. Schedule it as a one-shot `no_agent` cron job delivering to orion-ops; dry-run it by hand first. Before enabling a different provider, change the line it matches (`/v2/` masking, `# DISABLED` comment).
- Report the result as a pass/fail per check. Quote the provider's own error text and give the concrete options (upgrade the plan, switch provider, or shrink the chunk size, which costs ~200x more calls).

Volume, for sizing plans: ~22 `eth_getLogs` calls a day, a few multicalls, and ~2k calls for a one-time 90-day backfill. That is free-tier volume. A paid plan only buys range limits and throttling headroom.
