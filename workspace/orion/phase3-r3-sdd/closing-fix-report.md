## Concerns

1. **Resume uses `locator.rebuilt` counts, so it relies on two things:**
   - Each rebuild supersedes exactly one target with one new active row. That holds in supplyLevels.ts: one row per
     planned target.
   - No rebuild runs between s0 and s2 outside the block. If one did, `already` would include its rows. That is
     accepted: the add-up check still has to balance.
2. **expected.json format change.** An expected.json from a pre-R18 s0 has no `rebuiltRows`. Only `--resume` needs it,
   and it then STOPs with a clear message. Neither env has run s0 yet, so nothing is affected in practice.
3. **Partial purge inside one asset.** The purge is per asset and should be atomic. The s3 resume rule still accepts a
   partly purged asset if the counts add up, and checks its `withoutReplacement` only as an upper bound.
4. **The pre-check can now be skipped more often.** It is skipped whenever a post-switch levels job has started by the
   time of the jobs read. The unexempted post re-check is unchanged, so safety does not depend on the pre-check.
5. **The step-4 hand recovery is documented as prose only:** run `r3_check.py levels-job` / `levels-post` on fresh
   reads. No script was added for it.
